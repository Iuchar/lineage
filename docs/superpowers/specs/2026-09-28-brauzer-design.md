# Браузерная сборка: инструмент целиком на странице

Составлено 28 сентября 2026. Замысел согласован после разбора: сервера пока нет и платить за него не за что,
а показать работающий инструмент нужно уже сейчас — по ссылке, которую открывают без тебя.

## Зачем

Приложение живёт как сервер на Python: он считает раскладку, держит базу, ведёт журнал, проверяет доступ.
Страницы вроде GitHub Pages отдают только готовые файлы и ничего не запускают. Значит либо показывать
картинку без правки, либо перенести сервер внутрь браузера гостя. Выбрано второе: человек должен зайти,
потыкать, что-то внести, выгрузить и убедиться, что инструмент рабочий, а не нарисованный.

## Что уже проверено

Опытом, а не рассуждением (`.work/pyodide-test.html`):

- Python 3.13 поднимается в браузере за 1,3–1,6 секунды;
- `sqlite3` доступен отдельным пакетом, версия 3.39;
- `pydantic` 2.10 и `fastapi` 0.141 ставятся за 0,8–2,7 секунды;
- наше приложение отвечает на запрос по ASGI, без всякой сети.

Единственная преграда: FastAPI уводит синхронные обработчики в поток, а потоков в браузере нет. Лечится
подменой `run_in_threadpool` на прямой вызов в трёх местах (`starlette.concurrency`, `fastapi.routing`,
`fastapi.dependencies.utils`). Переписывать роуты на асинхронные не нужно.

## Устройство

Четыре части, каждую можно понять и проверить отдельно.

**1. Ядро (без изменений).** Папка `server/app` едет в браузер как есть: разбор GEDCOM, база, журнал,
уровни видимости, связки. Ни одной ветки «если браузер» внутри ядра не появляется — иначе поведение
витрины и настоящего сервера начнёт расходиться, и проверка на витрине перестанет что-либо значить.

**2. Мост (новое).** Модуль `web/src/api/bridge.ts` поднимает Python, распаковывает ядро, накладывает
подмену потоков и подменяет `fetch`: запросы к `/api/…` уходят в приложение внутри страницы по ASGI
и возвращаются обычным `Response`. Клиентский код не меняется вовсе — он по-прежнему говорит «серверу».

**3. Хранение (новое).** База и папка снимков лежат в постоянной файловой системе браузера (IndexedDB
через `IDBFS`). Закрыл вкладку, вернулся завтра — правки на месте. У каждого гостя своя база, чужих правок
он не видит. Первый заход разворачивает эталонные роды, которые лежат рядом со страницей файлами `.ged`.

**4. Сборка и публикация (новое).** `npm run build:web` собирает страницу вместе с ядром и эталонными
родами в `docs/` (или `dist-pages/`), откуда GitHub Pages её и отдаёт. Обновление — обычный `git push`.

## Что работает и чего нет

Работает всё, что есть сейчас: просмотр в пяти стилях, легенда, карточка человека, правка с журналом и
откатом, метки, связки между родами, уровни видимости, загрузка своего файла `.ged` и выгрузка.

Не работает по природе витрины:

- общие данные: у каждого гостя своё дерево, правки одного не видны другому;
- ссылка зрителям, выданная в браузере, никому не откроется — её некому обслуживать;
- вход редактора остаётся как показ устройства: проверка идёт на той же машине, где сидит гость, поэтому
  защитой она не является. На настоящем сервере тот же код защищает по-настоящему.

Об этом честно говорит сама страница: при первом заходе — короткая заметка о том, что это витрина, данные
лежат в браузере и никуда не уходят.

## Цена

Первый заход: около десяти мегабайт и три-пять секунд до появления дерева. Дальше браузер берёт всё из
кеша. На время загрузки страница показывает не пустоту, а заставку с именем инструмента и строкой
состояния.

## Проверка

- Тесты ядра остаются как есть и гоняются на настоящем Python: витрина ничего в них не меняет.
- Клиентские тесты (`vitest`) получают мост-заглушку, чтобы проверять разметку без Python.
- Отдельная проверка в браузере: страница поднимается, дерево рисуется, правка сохраняется, перезагрузка
  страницы её не теряет, выгрузка `.ged` даёт тот же файл, что и настоящий сервер.

## Чем это кончится

Ни одна строка серверного кода не выбрасывается. Когда появится сервер и домен, та же папка `server/app`
уезжает туда (этап 9: образ, обратный прокси, бэкапы), а браузерная сборка остаётся витриной для показа.

## Порядок работ

1. Мост и запуск ядра в браузере; страница поднимается и отдаёт дерево.
2. Постоянное хранение: база и снимки переживают перезагрузку.
3. Эталонные роды и первый заход: заставка, заметка о витрине.
4. Сборка страницы и публикация на Pages.
5. Проверка в браузере по списку выше.
