# Браузерная витрина — план работ

**Цель:** ссылка на GitHub Pages, по которой любой открывает инструмент целиком: смотрит деревья, правит,
выгружает `.ged`; данные живут в его браузере.

**Замысел:** `docs/superpowers/specs/2026-09-28-brauzer-design.md`. Ядро `server/app` едет в браузер как
есть, мост подменяет `fetch`, база лежит в хранилище браузера, страница собирается в `docs/`.

**Чем делается:** Pyodide 0.28 (Python 3.13 в браузере), micropip для `fastapi` и `pydantic`, IDBFS для
постоянного хранения, наш существующий Vite-проект для сборки страницы.

## Общие условия

- Ядро `server/app` не получает ни одной ветки «если браузер»: расхождение поведения обесценивает витрину.
- Сборка ядра для браузера делается скриптом, руками файлы не копируются.
- Каждая задача заканчивается проверкой в браузере своими глазами, а не «должно работать».
- Серверные тесты (`pytest`) и клиентские (`vitest`) остаются зелёными после каждой задачи.

## Задача 1: мост

**Файлы**
- Создать: `web/src/api/bridge.ts` — поднимает Python, распаковывает ядро, подменяет `fetch`.
- Создать: `web/scripts/pack-core.mjs` — складывает `server/app` и эталонные `.ged` в `web/public/core.zip`.
- Изменить: `web/src/main.ts` — перед стартом ждёт мост, если страница собрана витриной.
- Изменить: `web/package.json` — команда `build:pages`.

**Что получается:** страница открывается, дерево рисуется, данные приходят из Python внутри страницы.

- [ ] **Шаг 1.** Скрипт упаковки: `node scripts/pack-core.mjs` кладёт `core.zip` в `web/public`, внутри
  `app/**` и `gedcom/*.ged`. Проверка: файл появился, весит меньше мегабайта.
- [ ] **Шаг 2.** Мост: `startBridge()` грузит Pyodide с CDN, ставит `sqlite3`, `fastapi`, `pydantic`,
  накладывает подмену потоков (`starlette.concurrency`, `fastapi.routing`, `fastapi.dependencies.utils`),
  распаковывает `core.zip`, ставит `RODOSLOVNYE_DB=/data/rodoslovnye.sqlite3`, импортирует `app.main`.
- [ ] **Шаг 3.** Подмена `fetch`: запрос к `/api/…` превращается в вызов ASGI-приложения, ответ
  собирается в обычный `Response` с теми же заголовками и кодом.
- [ ] **Шаг 4.** Проверка в браузере: открыть собранную страницу, убедиться, что `/api/health` отвечает,
  а дерево рода рисуется.
- [ ] **Шаг 5.** Коммит.

## Задача 2: хранение

**Файлы**
- Изменить: `web/src/api/bridge.ts` — монтирование IDBFS и сохранение после каждой правки.

**Что получается:** правка переживает перезагрузку страницы.

- [ ] **Шаг 1.** Монтировать IDBFS в `/data`, при старте вызвать синхронизацию «из хранилища в память».
- [ ] **Шаг 2.** После каждого запроса, который менял данные (метод не `GET`), сбрасывать ФС в хранилище.
- [ ] **Шаг 3.** Проверка в браузере: сменить титул рода, перезагрузить страницу, убедиться, что титул на
  месте; отменить правку журналом, перезагрузить, убедиться, что отмена тоже сохранилась.
- [ ] **Шаг 4.** Коммит.

## Задача 3: витрина

**Файлы**
- Изменить: `web/src/api/bridge.ts` — первый заход разворачивает эталонные роды.
- Создать: `web/src/panel/firstrun.ts` — заставка загрузки и заметка о том, что это показ.
- Изменить: `web/src/styles/app.css` — вид заставки.

**Что получается:** гость на первом заходе видит готовые деревья и понимает, где он.

- [ ] **Шаг 1.** Если база пуста, загрузить эталонные `.ged` через `import_clan` и завести редактора
  с простым паролем для показа режима правки.
- [ ] **Шаг 2.** Заставка: имя инструмента и строка состояния («поднимаю Python», «разворачиваю роды»),
  снимается, когда дерево готово.
- [ ] **Шаг 3.** Заметка о витрине один раз на браузер: данные лежат здесь, к автору не уходят, ссылки
  зрителям работают только на настоящем сервере.
- [ ] **Шаг 4.** Проверка в браузере в чистом профиле: заставка, деревья, заметка, вход по паролю.
- [ ] **Шаг 5.** Коммит.

## Задача 4: публикация

**Файлы**
- Создать: `.github/workflows/pages.yml` — сборка и публикация.
- Создать: `docs/витрина.md` — как это устроено и как обновлять.
- Изменить: `web/vite.config.ts` — базовый путь для Pages.

**Что получается:** ссылка вида `tyr.github.io/rodoslovnye`, обновляется по `git push`.

- [ ] **Шаг 1.** Базовый путь сборки и команда `build:pages`.
- [ ] **Шаг 2.** Workflow: ставит Node, собирает страницу, публикует в Pages.
- [ ] **Шаг 3.** Документ: что живёт в браузере, чего на витрине нет, как обновлять, как потом перейти
  на настоящий сервер.
- [ ] **Шаг 4.** Проверка: открыть опубликованную ссылку, пройти весь путь гостя.
- [ ] **Шаг 5.** Коммит.

## Порядок и проверка

Задачи идут подряд: без моста нечего хранить, без хранения витрина бессмысленна, без витрины нечего
публиковать. После каждой — `pytest` и `vitest` зелёные, проверка в браузере своими глазами.
